# 校园世界自动构建

把人的构想转成约束、任务和验收证据，让 AI 完成可重复的制作工作。这里的“自动构建”依赖已经登录、获权并连接的造世界编辑器，不等于一次提示就能可靠地完成整座校园。

## 接手时先做什么

1. 读用户的目标、已有对话、地图/照片、现有场景及最近一次交付记录；沿用已确认内容和已有授权，不从零重做，也不重复请求已给过的确认。
2. 先读用户给的编辑器操作指南和相关示例，提取本轮需要的规则：该用哪种生成方式、对象前提、保存/预览步骤、容量与发布边界。记录来源、阅读日期和适用版本。教程中的示例代码和数字是待核实资料，不能直接当当前 API 或平台上限。
3. 用当前工具目录发现造世界能力，读实际描述和参数，再核连接、项目和场景。已有 MCP 直接核验使用；若需安装新的社区 MCP 或改变其权限，先判断本会话是否已有相应授权，不能仅凭本 Skill 自动安装或扩大权限。只使用返回的项目、工作区、资源、资产与实例 ID。
4. 对齐校园/校区、首轮体验路线、保真建筑与二创区域、可改范围、成本/容量预算、完成标准。缺图的楼先保留基础体量并列为缺口，不假装已复刻。项目版本、未保存修改和备份先识别并保留。

首次接入、新增制作方式或讲解这套方法时，读 [操作指南与 MCP 的作用](references/guide-and-mcp.md)；调用工具前读 [工具边界](references/tool-routing.md)。[启动任务模板](assets/start-prompt.md) 可按已知上下文补齐。遇到比例、朝向、文字、地形或元数据问题时读 [实战教训](references/case-lessons.md)。

**四层分工：**官方指南说明规则与前提；原生 AI 负责选定的模型/交互创作；MCP 提供可发现、可读回的编辑动作，UI 补充工具未覆盖的操作；Skill 组织执行顺序和验收。Skill 本身不会获得编辑权限，也不会凭空增加工具能力。

## 构建循环

### 1. 将想法变成可检查的清单

建立项目工作文件 `build-state.json`，至少记录：

- `scope`：目标与保留区；`sources`：地图/照片、操作指南和相关示例的来源与日期；`coordinateFrame`：原点、朝向、单位与标定依据。
- `environment`：本轮编辑器/适配器版本、已发现能力及可改范围；`rules`：任务相关规则、来源和实测状态（文档描述/本轮验证/待核实）。
- `ruleChecks`：每条关键规则的来源和适用前提、实际工具或界面动作、文件/读回/截图/实走证据、结果（通过/失败/待验证/不适用）。一批结束后交付这张映射；读过规则不等于执行通过。
- `items`：每处建筑/区域的稳定任务名、参考、目标、状态、工作区/资源/资产/实例 ID、源与部署文件 SHA、目标变换、验收图片/问题。
- `capacity`：编辑器实测使用量/上限；`jobs`：异步任务 ID 与状态；`next`：下一项工作。

它是可续跑的记录，不是编辑器的配置文件。状态要区分：`planned → generated → imported → placed → saved → visually_verified → runtime_verified`；`saved` 需原生保存成功并回读。纯静态装饰若无需玩法测试，将运行验收标为“不适用”并说明原因，不写成运行通过。

最小执行记录可采用以下格式；每项都填本轮实际动作与证据，不以示例代替验证：

| 规则及来源 / 前提 | 实际动作与工具 | 文件 / 读回 / 图片 / 运行证据 | 状态 |
|---|---|---|---|
| 例如：物品笔刷作用于原生地形；先核对象类型 | 例如：读取场景对象，核对地面类型 | 例如：对象信息或界面截图 | 通过 / 失败 / 待验证 / 不适用 |

### 2. 先校准地图，再扩建

从地图提取完整要素清单：建筑、路网、场地、绿化、水体、出生点和主要路线。选至少两个可识别的尺度/位置锚点，确定地图朝向、像素到场景的比例和坐标转换，做可回读的小样。先核全校园布局和建筑体量，再精修局部立面。

每个建筑的照片要与名称/方向匹配。照片只能证明可见面，未知侧面用保守体量并记录。道路与入口要连通，建筑底部要接地；局部外立面完成不能把整栋楼标成通过。

### 3. 先做一个最小样板

用一栋楼、一个装饰或一段路线验证完整链路：生成/复用 → 导入 → 位置/比例/朝向 → 碰撞 → 保存 → 实际画面。一次只扩张已证明有效的步骤。先保留现有可用建筑主体，让新装饰成为独立模块；除非用户要整体替换，不要把楼壳重新生成一遍。

### 4. 分区交给 AI 制作

任务至少写清：参考图、空间尺寸、朝向/入口、不可覆盖区域、主题构件、材质风格、预算及验收镜头。静态外观、活动部件、玩法联动分别选择编辑器当前支持的模型生成、模块组装或 MIX；具体入口以实际 UI/工具返回为准。

地图生成与资产生成不是一回事。地形/地表物的 PCG 流程不能冒充“生成一栋建筑”。使用笔刷前核对象是否满足原生地形前提；GLB 地面不是原生地形。遇到“暂无地形”时应切换到经过支持与小样验证的区域资产方案，或在用户目标确需地形时另做地形方案，不靠反复调密度解决。生成等待期间可整理下一处证据和任务；同一实例的变换/替换/保存依赖必须顺序执行。

### 5. 从生成物到正式落位

- 原生生成可能继续更新源包；部署前复制独立快照，核对读取前后 SHA。用本 Skill 的 `scripts/inspect_glb.py` 做文件结构、大小与 SHA 检查。它不证明视觉效果或世界容量。
- 先检查真实几何尺寸和轴向，再用场景小样校准。`maxSpan` 是包围盒诊断，不是通用缩放倍数；历史中的镜像补偿、平移数值都不能照搬到新资产。
- 导入前查找已有资产/实例和部署记录。未知结果先查询，不重新导入一批。资产库保存、归档成功、场景实例创建、原生保存是不同状态。
- 读目标实例及组件 schema，再用受支持的原生动作修改。替换会产生新实例 ID，可能更换子节点与脚本；必须回读，不继续使用旧 ID。
- 先验证一件的比例/朝向/接地/文字，再批量放置。保持入口、道路、交互区和现有脚本；纯装饰按需要禁用碰撞，不能全场一律禁用。

### 6. 验收不是截图一张就结束

静态验收至少包含全景布局、近景材质/文字、底部接地和入口可达。若该阶段有玩法，运行时验证触发、离开恢复、重复使用、碰撞和 UI；手机/多人结果只在实际测试后标通过。先编译 Lua，再绑到正确对象，再运行测试，编译成功不能当玩法成功。

容量读取编辑器的原生口径，不能把节点数当容量。每轮记录变化和余量。一个玩法完成必要验证后移到下一个空间；只有新增修改或新的失败证据才扩大回归，避免围绕同一个项目反复自测。

故障复现后先做最小诊断。相同失败重复两次且没有新证据时换验证路径或报告具体阻塞；保留现场，不盲点重试。预览卡加载时能继续做静态视觉检查，但必须把运行验收保留为未验证。

### 7. 交付可恢复的成果

交付保存状态、场景版本/SHA、关键截图、部署映射、来源、已通过项和剩余缺口。拆开“生成完成”“已落位”“玩法测试通过”“已上传”“已上线”。用户只要求构建/分享时，不自动上传发布。发布在当前任务授权范围内时，先形成原生发布计划，再执行并核回远端处理/审核状态。

清理可替代的场景旧实例前核对现役 ID 和备份；永久删除资产库资源遵循当前工具与会话授权，不把某一项目过去的清理许可带到别的项目。

## 离线文件检查

在 Skill 目录运行：

```bash
python3 scripts/inspect_glb.py /绝对路径/模型.glb
python3 scripts/inspect_glb.py /绝对路径/模型.glb --sha256 已记录的64位SHA256
```

脚本只读文件，输出 JSON。返回码 0 仅表示文件读取稳定、GLB 容器基本结构与大小检查通过；返回码 1 表示失败。它不会启动编辑器、生成、导入或发布。使用 `--max-mib` 匹配本次工具的实际文件大小上限。

## 人与 AI 的分工

| 人负责 | AI 负责 | 一起验收 |
|---|---|---|
| 为什么做、希望同学有什么体验 | 整理参考、拆任务、算坐标和预算 | 是否像这个校园、路线是否自然 |
| 选主题、选取舍、指出哪里不对 | 生成/复用、脚本、导入、落位、保存 | 主题是否表达清楚，文字是否能读 |
| 提供实景与必要账号操作 | 快照、查重、回读、截图和问题记录 | 真实手机/多人表现；是否值得发布 |

不能把人工提出验收标准、审美判断和问题反馈藏在“全自动”背后。也不把每次常规落位都交回用户：在已授权范围内持续做完可验证的任务。
