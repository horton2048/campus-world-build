# 北工大案例：从失败走到下一步

依据 2026-10-10 至 10-26 的制作记录，2026-10-30 重审。下文区分**当时已验证的修复**和**从失败提炼、下一轮必须执行的路径**；后者不是补记历史成功。原始会话、场景、照片与账号资料不随仓库公开。历史数字用于解释问题，不能当作编辑器现行限制。

## 先守住实际目标

最初目标已经明确：**官方地图决定布局 → Agent 自行逐栋找真实照片 → 依图生成 → 全校建筑、道路和场地补齐与接地 → 保真精修 → 再考虑玩法。**用户后来反复催补楼、找照片和“继续”，主要是在纠正执行偏离，不是最初没说清需求。完整诉求与实际偏差见 [原始目标与工作流](intent-and-workflow.md)。

小样用于证明制作方法；批次可以小，总范围不因此变小。以下各条都应回到全图清单，而不是变成一串脱离校园目标的技术实验。

## 1. 缺楼、薄片楼与悬空：先把覆盖清单变成任务选择器

- **真实证据：**用户指出学院楼缺失和悬空后，Agent 才按 70 处建筑/组团审查，发现 48 处缺完整楼体、8 处仍为局部立面。后续另一时点统计为 47 处主体/外壳、8 处局部、15 处无楼体，且没有一栋通过全部验收。这是不同时间的状态，不能混成最终成果。
- **失败机制：**用资产包数、入口、正面照片或局部能走代替整栋覆盖；全图清单没有持续约束下一项，局部路线和装饰占用迭代。
- **下次成功路径：**开工建立地图对象全集，与场景逐项匹配；分别标明占位、局部、整栋、照片精修和验收状态。每批末从“未做/缺完整体量、场地 → 位置/接地 → 照片相似度 → 细节”取下一项。校门、道路、球场等也在清单中，不只列楼。
- **通过证据：**每个地图项都有真实名称、照片/依据、资产包及场景实例映射；整栋体量、楼翼、屋顶和入口可核；全图无漏项，未达标项不计入已完成。合包仍能单独定位、预览每栋。
- **边界：**历史中建立了更完整的验收与补齐记录，但没有证据证明最终全校逐栋照片保真、全周接地和运行全部通过；上述全量闭环是待执行的交付门槛。

## 2. 用户被迫补照片：研究工作本就属于 Agent

- **真实证据：**最初要求就包含逐栋真实检索；后续用户仍需再次强调每个学院楼要有实景照片、缺图就主动找。已有图库不代表清单中每栋都具备足够依据。
- **失败机制：**生成队列与照片清单脱节，看到可用盒子/旧资产就继续，随后由用户发现不相似或漏楼。
- **下次成功路径：**从官方地图固定校园身份，按官网、学院/官方新闻、可核实公开实景逐栋查图；实际看图，核学校、校区、年代、楼名、正侧背面。照片不足就换来源、关键词或继续其他已就绪对象，保留已查范围；仅真正身份冲突集中问用户。
- **通过证据：**每栋有来源、图像身份依据、可见角度与缺口；“没找到”和“已核参考”分开。生成任务绑定该图组，未核背面和尺寸明确标估算。
- **边界：**不能承诺每座校园的所有背面都能从公开资料找到；不能用其他学校的同名楼凑图。估算外壳可作中间态，不能冒充照片复刻通过。

## 3. 约 1.88 倍比例错误：按导入来源校准一次，再复用

- **真实证据：**早期把本地导入归一化公式套到云端 AI 资产，部分楼约大 1.88 倍；用已知 28 米对照杆在原生视口检查并修正。后续所用导入路径保留源米制，不再乘最长边。
- **失败机制：**混淆模型源尺寸、导入器归一化和场景缩放；把某一路径的 `maxSpan` 公式当通用规则。
- **已验证修复：**先保留可回退版本，读源模型包围盒和场景变换，与独立已知尺寸对照；仅对错误环节修正，并在原生视口复核大小、朝向与接地。校准结果只复用于同类来源和同一导入链。
- **通过证据：**源尺寸、目标尺寸、转换理由、导入后读回、对照物近景一致；接地没有因缩放再次破坏。
- **边界：**28 米是该案例对照物，1.88 是当时错误倍率，都不是所有学校的参数。原校园图转换仍是工作估算，不能称测绘精度。

## 4. 楼朝向对了，字却镜像：几何与纹理分开验

- **真实证据：**后期模块落场后出现文字镜像；修正资产替换、变换回读、近景和原生保存都有记录。
- **失败机制：**轴向反射改变可读纹理；只检查建筑方向，没检查校名和符号。整张图盲翻又可能破坏共用图集的其他部分。
- **已验证修复：**定位实际轴向补偿，分别比对几何与文字；只修相关文字/符号 UV 岛或独立纹理，保留其他几何和图集。导入新候选、替换现役实例、回读变换、核字、保存。
- **通过证据：**原生近景字可读，楼体朝向与地图相符；无相关几何/材质回归，源与部署资产有版本对应。
- **边界：**不能无检查地给所有 GLB 固定 X 反射或整图翻转；静态字正确不证明玩法、手机或多人通过。

## 5. 草刷不出来：先查对象前提，再换受支持方法

- **真实证据：**已读教程要求在地形表面绘制；实际校园底板是 GLB，UI 提示“当前场景暂无地形”，草数量 0 → 0。之后三片区域草层有原生归档、落位、保存和局部穿行记录。
- **失败机制：**把 GLB 地面当原生 Terrain；重复调笔刷参数不能改变承载类型。
- **已验证替代路径：**停止无效笔刷，核地面类型和当前官方能力；按真实绿地、道路及步道边界生成合批短草层，经原生生成/编辑入口完成入库、落位和局部测试。
- **通过证据：**新增草层实际存在且边界不侵占道路；读回与保存成功，近景和局部穿行通过。
- **边界：**不能说笔刷最终成功，也不能说全校草地覆盖、全路线或手机性能已通过。若新项目使用真正原生地形，可重新验证笔刷，不必照搬替代方案。

## 6. 合包太大与场景快满：批量前就约束预算

- **真实证据：**五栋合包 35,748 面被当时 30,000 面上限拒绝；后续发现多个超限包，拆分并保留坐标。另一次最终原生容量为 3610/4000，工具节点数 4168 是另一口径。
- **失败机制：**批量生产后才检查入库限制；面数、包大小、渲染实例、场景容量被混成一个指标。
- **已验证修复：**拆成符合当时限制的建筑组，保留世界坐标，逐包核比例与映射。新任务先读当前限制和容量、实测一件同来源资产，再把预算写入生成任务；后续批次持续检查余量，按适合方式合批或简化。
- **通过证据：**文件检查、入库、实例数与原生容量分别有记录；拆包后位置和全量建筑对应不丢失，保存回读通过。
- **边界：**30,000 面和 4000 是历史版本案例，不硬编码为新项目上限；节点数不等于原生容量，不能靠删验收对象腾空间。

## 7. 射线大多命中，人却掉下去：失败候选撤回

- **真实证据：**一次绿化候选 53 个采样点中 52 个命中，人物实走仍掉落；该失败候选被撤回，没有计为成功。
- **失败机制：**将采样命中率、入口可走或单角图当连续通行与全周接地证明。
- **已验证处置：**记录掉落位置和运行结果，撤回失败候选，恢复已知可用状态。后续修复应分别检查表面、碰撞、台阶/坡道和实际人物路线，完成相关回归再入场。
- **通过证据：**几何与可见接地检查，以及真实角色连续路线两套证据；中断、重生、穿模均不能记为连续通过。
- **边界：**已验证的是撤回和保留缺口，不是这一候选后来已修好。单条路线通过仍不能替全周、全校、手机或多人验收。

## 8. 一直测同一个项目：通过后必须返回全图队列

- **真实证据：**用户指出跑步项目回归耗时过长，随后再次指出篮球场仍缺；现场核查发现该球场区只有底板。
- **失败机制：**局部测试缺少退出条件；选择更容易验证的项目，取代整体覆盖推进。
- **下次成功路径：**为本轮修复限定需要的验收；通过即保存并取下一个全图缺项。只有相关改动、新失败或明确测试缺口才重新扩大回归；同法两次失败而无新证据，换受支持方法或保留阻塞并转可做项。
- **通过证据：**每批全图未做/待修正数量或证据缺口实际减少；已通过的局部没有无依据反复测试；未完成基础项不被玩法遮盖。
- **边界：**这是一条由历史失控提炼的循环约束，不是历史执行已始终遵守的事实。为赶进度跳过必要修复回归同样不算成功。

## 9. 已提交却没有产物：恢复先查事实，不重发任务

- **真实证据：**七项美化曾开始并读取参考照片，后续接手发现全都中断、没有可部署模型；之后先完成源与 GLB 检查，再入场，最后才修文字并保存。
- **失败机制：**提交、任务运行、产物、入库、实例、保存、视觉和运行被合并成“完成”；会话中断后无可靠任务/版本记录就重试，易产生重复付费、资产或实例。
- **可执行恢复路径：**每次有副作用的动作前保存对象、输入版本/哈希和操作意图；返回后立即记录真实任务/资产/实例句柄。中断先查同一任务，再核产物、资产库和现场。观察超时只是未知；只有确定失败、取消或不存在并核对无落地副作用后才重新提交。没有查询入口时保留未知，先做独立资料工作，不能猜失败。
- **通过证据：**恢复后能说明唯一当前版本、同一任务状态、是否已有资产/实例及下一步；同一输入未被盲重做。入场后单独核保存和视觉；运行未测仍待验。
- **边界：**历史证明分阶段恢复和最终静态部署可行，不能据此声称“任意断点自动无损恢复”已实测。任务记录不是活进程证明；真实运行状态必须重新查询。

## 10. 源模型变了，旧检查还在：部署绑定稳定快照

- **真实证据：**原生生成模型曾在导入准备中被 AI 更新；当时通过连续一致读取建立独立快照，输出后再次核源 SHA。
- **失败机制：**用可变化路径指代部署版本，尺寸和纹理核验可能属于另一个文件。
- **已验证修复：**等待源稳定，做只读检查与独立候选快照，保存哈希和生成输入；导入前后再核对应关系。源一旦变化，旧尺寸/纹理结论不自动沿用。
- **通过证据：**稳定读取、候选哈希、已导入版本与场景映射一致。
- **边界：**哈希一致仅证明字节版本，不证明正确尺寸、文字、碰撞或原生保存。

## 11. 接口成功不等于画面成功，作者报告也不是平台字段

- **真实证据：**`focus` 返回成功，截图仍停旧帧；恢复普通窗口并用原生聚焦和坐标轴操作才取得新近景。作者 meta 混入 `candidatePlacement`、`sourceGeneration` 曾被拒绝，后将报告移至输出文件、保留已验证字段。
- **失败机制：**把工具 success 当作画面已更新，或凭语义猜平台 schema。
- **已验证修复：**读当前工具 schema；元数据只写受支持字段，作者过程另存。每次截图实际辨认对象、视角和新变化，必要时用当前受支持 UI 刷新/聚焦后再核。
- **通过证据：**接口读回与正确当前视图互相印证；meta 被正常接受，作者报告仍可追溯。
- **边界：**不能用截图工具返回 success 替代看图；也不能绕过官方/已获权入口直接改场景缓存。

## 这些教训怎么进入日常循环

一栋/一区只在对应证据通过后推进状态：**图组与身份 → 生成候选 → 源检查 → 入库 → 入场与变换回读 → 接地/通行 → 原生保存 → 视觉/必要运行验收 → 更新全图 → 下一项。**资料研究可以与生成等待交错；同一场景只由一个负责人写入。

把完整日志和大图留在文件中，当前工作记录只留目标、全图索引、当前版本、在途句柄、已查缺口和明确下一项。每次恢复重新查当前任务/场景，不把上一段摘要的“在运行”当实时事实。上下文与长程执行的具体约定以 Skill 主文件指向的运行说明为准。

七处后期美化有落位、保存、变换读回、文字可读与原生近景证据；四站校园护照曾有正式出生点连续步行 4/4 的历史记录。这两类成果属于不同阶段，不能互相补验。部分最终预览卡加载，旧资产库清理仍有待办，均须保留缺口。没有证据支持全校园全部精细复刻、手机/多人/性能验收或公开上线。
